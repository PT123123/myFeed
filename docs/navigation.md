# 抽屉与页面归属：一件事只在一页里管

日期：2026-09-27（1.4.7 / versionCode 14）；2026-09-28 追加 1.4.8 / 15 一节
状态：**代码、单测、装机完成**；新排版的观感没人眼看过（见文末）

## 为什么要拆

1.4.6 把「电脑端要做的事」放进了设置页 → 「我添加的源」下面第四行，用户提了两句意见，都成立：

- **那条链的一半根本不在手机上**，把它排在「添加订阅源」「从 OPML 导入」后面，等于暗示它是
  订阅列表的一个附属开关；而它实际管的是另一台机器上的登录、采集节奏和服务生死。
- **抽屉里的「分类」分组和首页那排 chips 是同一批东西**（都从 `state.scored` 派生，见
  `FeedSources.categoriesOf`）。两处都能选「中文代码开发」，但只有一处会跟着内容变化更新，
  于是同一屏出现两个真相来源。

顺带把「兴趣」也拆了：兴趣词、召回通道、搜索 key、语义模型回答的是
**「首页为什么是这些内容」**，而暗色模式、缓存上限、清理已读回答的是**「这台设备怎么用顺手」**。
混在一页里，调一次兴趣词要滚过十几行缓存设置。

## 现在的结构

抽屉（`FeedReaderApp.kt`，`ModalNavigationDrawer`）四项：

| 项 | 去哪 | 里面管什么 |
| --- | --- | --- |
| 全部文章 | 回首页并把筛选落回「全部」（含清掉「只看某条源」） | 内容流本身；分类筛选只在首页那排 chips 里 |
| 兴趣 | `InterestsScreen` | 兴趣词、召回通道、自建 RSSHub、AI/全网搜索 key、语义模型 |
| 电脑端采集 | `RelayScreen` | relay 地址与状态、**这台电脑采到的内容（每条源一行，点开只看它）**、连接自检、手动同步、扫一扫、自动同步开关、整份「电脑端要做的事」清单 |
| 设置 | `SettingsScreen` | 订阅源（自建 + 内置）、阅读、搜索引擎、缓存与清理、关于 |

抽屉里不再有「分类」。设置页标题从「兴趣与设置」改成「设置」。

页面切换是一个 `rememberSaveable` 的 Int（`PAGE_NONE / PAGE_INTERESTS / PAGE_RELAY / PAGE_SETTINGS`）
而不是枚举：转屏幕之后要能从 Bundle 里认得回来，枚举能不能存取决于版本，不值得赌。
`opened != null`（阅读页）仍然优先于页路由，返回顺序就是「阅读页 → 那一页 → 首页」。

## 电脑端采集那一页

`ui/RelayScreen.kt`。三行状态来自新增的纯逻辑层 `data/RelayStatus.kt`：

| 行 | 数据来源 | 为什么是它 |
| --- | --- | --- |
| PC 地址 | `settings.relay_base_url` | 只有同步成功过才会写进偏好，所以这一行等于「上次能用的是这台」 |
| 来自它的订阅 | `RelayStatus.endpointCount(base, allSources)` | 按**主机 + 端口**数，换过 IP 之后老地址已被原地改掉，数字不该翻倍 |
| 上次读到清单 | `viewModel.relayLastSyncAt` | 只有**读成功并落库**的同步推进它（手动与静默都算）；连不上不改这个数 |

第三行特意不叫「上次同步成功」：`relay_last_sync_at` 那个偏好键是静默同步的节流戳，失败也算一次
尝试，直接拿来显示会把「去过但没连上」说成「读到了」。所以在 `FeedViewModel` 里另开了一条
只用于展示的 StateFlow，语义与那边分开。

清单正文用 `RelayGuidance.pageSections(focus)`：

- `focus = null`（从抽屉进）就是整份五段清单，顺序不变；
- `focus = 某个 RelayIssue`（从首页失败横幅点进来）把对症那段摆到第一屏；
- `FIRST_RUN` 的对症段与「第一次接入」那节同名，按标题去重，不会在同一页摆两遍。

末尾多一节「这份清单管不到什么」，把两件手机确实看不见的事写明：那边最近一次采集时刻要跑
`harvest list` 才知道；知乎订阅只有摘要，整篇要电脑端逐条取详情（见
[offline-full-text.md](offline-full-text.md)）。

## 追加（1.4.8）：「电脑端采集」这一页得先能看见内容

拆完页之后用户提的第二轮意见：**「这一页里全是设置，我找不到该从哪看电脑端采来的东西」**，
以及「电脑端我自己就能联调，你可以在手机端去看的」。量了一遍，两件事都成立，但成立的方式不同。

链路本身是通的（2026-09-27 23:2x，他那台平板 ↔ PC `192.168.1.20:8099`）：

| 检查 | 结果 |
| --- | --- |
| 设备侧网络 | `nc -z 192.168.1.20 8099` 通；`curl feeds.opml` → 200 / 24ms；`curl zhihu-sample-zhi-75-54.xml` → 200 / 58677B |
| App 偏好 | `relay_base_url=http://192.168.1.20:8099`、21 条 `zhihu-*.xml` 源在位、`relay_last_sync_at` 在位 |
| 手机缓存 | 20 个 relay 源文件共 **420 条知乎回答**，写入时间就是量的前几分钟；`zhihu-sample-bei-jiu` 一条都没有（PC 侧那份 XML 里 `<item>` 为 0，不是链路坏） |
| PC 侧 | `harvest/out/zhihu-*.xml` 那 21 条合计 **477 条 `<item>`**；`state/*.json` 的 `last_run_at` 都在 18:30–18:39 |

也就是说「拿不到」不是网络层的事实，而是**在界面上认不出来**：那 420 条的 `pubDate` 是回答原文的
时间（2021 / 2024 居多），排序按新鲜度，于是它们全沉在首页列表底部；而唯一能把它们筛出来的
分类词叫「自建」—— 那个词回答的是「这条源怎么加进来的」，不是「内容从哪来」，用户筛不到答案。

477 与 420 那 57 条的差也在这里查清了：`RssParser.MAX_ITEMS` 每条源只留 30 条
（`4×(39−30) + 3×(37−30) = 57`）。这个数字必须写进界面文案 —— 否则电脑端 `harvest list` 报 39、
手机这一页报 30，看着就像「又少拿了」。

### 改了三件事

1. **`电脑端采集` 页加「这台电脑采到的内容」一节**（`RelayScreen`，判定在
   `RelayStatus.feedRows` / `rowLabel` / `totalItems`）。每条 relay 源一行：`37 条 · 最新 5 小时前`。
   **一条都没采到的源也摆出来**（文案是「手机上还没有它的内容」）—— 那正是「拿不到」这一问的答案所在，
   筛掉空源等于把唯一有信息量的那行藏起来。节标题下先声明 30 条上限。
   数据取自**首页那份列表**（`state.articles`）而不是另开一次缓存读取：同一屏不能有两个真相来源，
   首页翻不到的东西这一页也不该报出条数。代价是「已订阅源」通道关掉时这一节会全为 0。
   于是「0 条」被拆成三种说法，各有对症的那句：整节为空（PC 没跑 run / 通道关着）、
   有行但全为 0（清单读到了、内容没拿回来，接着指向下面的自检）、**只有部分行为 0**
   （电脑端本来就没采到，`harvest list` 里它也是 0，指向下面「源在列表里，但内容不对」那一节 ——
   文字指向，没做锚点跳转）。最后那种不写出来最危险：用户会把「那边没采到」读成「刚搬进来还没刷」，
   然后去删那条源。
2. **点一行 = 回首页并只看这一条源**。列表只有首页那一份实现，在这一页里再摆一份卡片
   等于以后改一处漏一处。状态是 `FeedReaderApp` 里的 `sourceFilter`（源 id，`rememberSaveable`）：
   - 与分类筛选**互斥**，同一个槽位的两种取值 —— 所以 chips 行不新增第二排，而是在最前面放一颗
     选中态的「只看 知乎 · 示例戌 ✕」，此时 `current` 传空串（让「全部」亮着等于同时说两句矛盾的话），
     点任意分类即清掉它；抽屉「全部文章」也清掉它。
   - 按 id 认不回源（删了、或换 IP 之后 id 变了）就当没筛：宁可显示全列表，
     也不要一个筛不出任何东西的隐形过滤器挂在顶上。
   - 空态那句话说的是那条源的名字（`EmptyPane(category = …)`），说「全部」会让人以为筛选没生效。
3. **一键连接自检**（`RelayScreen` 一行按钮 → `FeedViewModel.runRelaySelfTest`）。
   两步：**读清单**（复用 `syncRelay`，走 `auto = true` 的写法：不触发整轮刷新、不把用户亲手删过的
   条目偷偷加回来）＋ **抽查一条 feed**（复用 `FeedRepository.probe`，和「添加订阅源」同一套判据）。
   只读清单不够：`feeds.opml` 和各条 XML 是 harvest 分两步写的，只写过一半时前者照样读得到。
   三种结论分开说 —— 连不上（带上对症那节电脑端命令）/ 通了 / **清单读到了但抽查失败**。
   没配地址时不给测（按钮文案直说）；新搬进来的那几条要说「下拉刷新才有内容」，
   因为这一击刻意不刷整轮。

### 分类为什么改名，以及为什么不是迁移

relay 同步进来的源分类从「自建」改成**「电脑端采集」**（`SourceRules.RELAY_CATEGORY`，
新同步的那批由 `OpmlParser.parse(fallbackCategory = …)` 直接写对）。老数据靠
**读时归一**：`SourceStore.customSources` 的 getter 过一遍 `SourceRules.categoryFor`
（判据是主机 + 端口对上已确认的 relay 地址，同 `endpointCount`），所以下一次任何写回
（同步、加源、删源）会把它落正。

**没起一次性迁移**：那要多占一个偏好版本号键，而读到的分类和写回去的分类天然是同一份。
用户自己写过的分类（OPML 目录、手填的）一律不动，只兜那个默认值 —— 指向别的机器的自建源
仍然叫「自建」，那批内容确实不是那台 PC 给的。

## 追加（1.4.9）：同一页上第一次有能往回打的按钮，以及阅读页为什么白着脸

两个诉求来自同一句话：「点开文章后的阅读页白，我需要是黑暗模式的」＋「我需要它跟电脑端打配合，
有时候电脑端可以开启监听，手机端可以向它发起采集命令」。前者是**另一页**（阅读页，不在抽屉里），
后者落在「电脑端采集」这一页上 —— 抽屉四项一个字没动，也没新增第五项。

### 「让这台电脑再采一轮」那一节摆在哪、为什么摆在这

放在「订阅这份清单」和「电脑端要做的事（整份清单）」之间，四个动作一行一个：

| 动作 | 对面 | 为什么是这一行 |
| --- | --- | --- |
| 先看这一轮谁会跑 | `POST /command/plan` | 不碰网络、不打目标站点，是这一节里唯一**永远安全**的一击，所以排第一 |
| 让它采一轮 | `POST /command/run` | 副标题直说「限速、冷却、每日上限照旧生效」，免得以为这一击能绕过电脑自己的排程 |
| 只采这一条源 | 同上 + `{"feed":"<id>"}` | 只在已经列出内容（`feedRows` 非空）时才出现，点了开一个选源对话框（每行带 `37 条 · 最新 5 小时前`） |
| 重出它的订阅产物 | `POST /command/regen` | 离线那条：改了配置或换了地址用它，不采集 |

三条不是 UI 决定、但必须记着的：

- **没配对时这一节照样在，但话改成不承诺**。节标题的 caption 走
  `RelayStatus.commandAvailabilityLabel`：没配地址 / 只出静态 RSS（命令口没开）/ 命令会真打到那台电脑，
  三种形状。没配对时四个按钮按下去**不发请求**（`RelayCommandClient` 直接回 `NEEDS_TOKEN`），
  因为白跑一次网络往返换不来任何信息，而对面的 401 说的话和这里一样。
  以前那种「没配对就把整节藏起来」的写法被否掉了：藏起来他就不知道这件事**是可以做的**。
- **`run` 是受理不是跑完**。202 之后每 5 秒轮 `GET /command/status`，看到 `running=false` 才停并
  触发一次 `refresh`（`onRunFinished`）。轮询的第一个动作是 `delay` 而不是先发：刚回 202 时对面
  那个线程未必已经登记上，先发一次就会立刻读到 `running=false`，界面上一闪「完了」再变回「在跑」。
  轮询里读不到状态（服务关了）就当它结束了，不拿一个转圈的界面耗着他。
- **状态块多一行「命令口」**：`配过地址、扫过配对码之后才有` / `没配对：它只出静态 RSS` /
  `已配对：能让它现采`。它和「服务」「清单」那两行并列，是因为这一页原有的三行说的都是
  **手机能自己看到的东西**，而命令口配没配对、对面肯不肯接单，是这一版才有的第四种状态。

同一页上还有一处**被这句话自己推翻**的旧文案：「这份清单管不到什么」原来写着手机读不到最近一次
采集 —— 1.4.9 之后配了对的手机能读到（`/command/status` 里有 `started_at` / `finished_at` /
`outcome`），那句话改成了只说没配对时的实情。

### 深链多带一把钥匙，抽屉那一页因此多一句话

配对就是扫 `harvest serve --allow-commands` 那张 `/pair` 页上的码：
`myfeed://relay-sync?base=<编码过的地址>&tok=<token>`。扫码确认弹窗里因此**多明说一层授权**
（「这个码还带着配对钥匙：扫过之后手机能让它现采一轮」）—— 它是把「拿你的登录态去打站」的能力
交给手机，扫之前不说等于偷偷拿到。token 只认 `token_urlsafe` 的字符集、夹到 64 长度，可疑码
**只丢配对那一半**，地址照旧同步（`DeepLink.safeToken`）；换到另一台 PC（主机 + 端口不同）时
旧 token 会被清掉，那把钥匙不属于这台机器。

### 阅读页那一白不在这一页，但在同一次反馈里

点开文章那一页的离线全文是**应用自己渲染的 HTML**，配色以前交给 WebView 的
`prefers-color-scheme` 判定，而 Android 13 起那个判定跟的是 App 声明的主题资源 —— 仓库里只有
一份 Light 主题，于是夜里界面是暗的、这一页白着脸。改法是写死配色 + 补 `values-night` 那份主题，
细节和实测记在 [web-reader-dark-mode.md](web-reader-dark-mode.md)，这里只留一句：**能自己决定的
东西不交给 ROM**。

## 追加（1.5.0）：第一个能被 Obtainium 跟踪的正式包

1.4.9 之前每一版都是 `assembleDebug` + `adb install -r` 手动塞进平板的，GitHub 上连一条 Release
都没有 —— 也就是说没有任何更新渠道。这一版开始改走「tag + Release + APK 资产」，Obtainium 直接加
`PT123123/myFeed` 这个 GitHub 源就能收到更新。

- **版本**：versionCode 16 → **17**，versionName 1.4.9 → **1.5.0**。自升级只认 versionCode，
  不升上去 Obtainium 会一直显示「已最新」。
- **签名**：`app/build.gradle.kts` 里加了 `signingConfigs.release`，直接复用用户目录下那只
  Android SDK 自动生成的 debug keystore（`~/.android/debug.keystore`，别名 `androiddebugkey`）。
  这么选的理由是**手机上那台设备已经装着 debug 签名的 1.4.9**，换独立 keystore 会签名不符、
  只能先卸后装，把已读记录和缓存清掉。路径按 `System.getProperty("user.home")` 现算，
  不把本机绝对路径写进这份公开的构建脚本。
  - 代价记在这儿：这只 keystore 是 SDK 在这台机器上随机生成的，口令虽然是公开的 `android`，
    但文件不外泄就没人能签出兼容签名。真正要担的是「这只 keystore 丢了就得换新签名，
    老设备只能卸载重装」。将来若要上 F-Droid 之类需要可复现构建的渠道，得换成独立
    release keystore 并一次性迁移。
- **发布前把仓库里的个人信息抹干净**（仓库是 PUBLIC）：真实配对 token、局域网 IP `192.168.x` 网段、
  平板序列号、`C:\Users\...` 本机路径、以及测试夹具里那份 21 条知乎关注清单，全部换成合成占位值。
  夹具仍保持 21 条和「带大写下划线的那条」，因为契约测试钉的就是条数与大小写敏感这两件事。
